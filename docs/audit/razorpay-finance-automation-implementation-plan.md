## Error, UX, and Logging Requirements

- Preserve Razorpay's provider `code`, `description`, `source`, `step`, and `reason` only as sanitized diagnostics; do not display untrusted provider descriptions verbatim. Each CRM endpoint has a stable machine code, HTTP status, safe customer/operator wording, retryability, and correlation/request ID.
- Order-creation uncertainty: tell the customer not to retry while the provider result is checked; expose a functioning status action with visible loading/result/error feedback. Do not leave a flickering button or tell users to refresh a link as the only recovery.
- Pending/authorized/unknown: show payment checking/pending, suppress Pay, and provide status recovery. Failed: re-enable Pay only after provider-authoritative terminal failure and server eligibility checks. Captured: show paid and remove Pay.
- Retry timing is provider-state-driven; there is no elapsed-time timeout that automatically unlocks Pay. Recheck status on the customer's explicit action and through the existing recovery path. Keep Pay suppressed for `CREATED`, `PENDING`, `AUTHORIZED`, or unknown/provider-unavailable states, regardless of how long they persist. Unlock only after an authoritative terminal failure (then re-run server eligibility/idempotency checks), or after provider confirmation that the existing Order is still `created` with zero attempts and no Payments so the same Order can safely resume. If a state remains unresolved, direct the customer to contact support/Finance review; never advise another payment or create a new Order just because a timer expired.
- Audit events must identify actor/source, invoice/local attempt/provider Order/payment/refund/event IDs, mode, amount/currency, transition, outcome, error code, duration, and correlation ID as permitted. Keep browser telemetry explicitly non-authoritative. Redact secrets, signatures, OTP, full PAN, bank credentials, and unnecessary personal fields.
- Required visible actions only: Pay, Check payment status, Finance-authorized reconciliation/review, and Finance-authorized refund where applicable. No controls that perform no action; no extra payment method selector that contradicts Razorpay Checkout.
- Responsive/accessibility checks apply to the dry-cleaning checkout and relevant Finance views only: 320/390/768/1440px, keyboard/focus, readable statuses/errors, long references, loading/empty/error/permission-denied states, and no horizontal overflow.
