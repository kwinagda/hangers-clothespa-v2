## Objective

Build a reliable, auditable payment lifecycle where a successful Razorpay collection is reflected once in the Hangers financial ledger and then appears consistently in the invoice, order, customer, receipt, Accounts Receivable, Finance, and reports. Failed, delayed, duplicate, out-of-order, disputed, refunded, or unmatchable events must be visible and recoverable without creating duplicate money movement or falsely marking an invoice paid.

The design must be engineered and load-tested for the stated ambition of **₹1 crore of checkout value per day**. That is a volume target, not a promise of availability, throughput, or settlement timing. Capacity, provider limits, queue lag, database contention, and operational staffing must be measured before claiming the target is met.

## Primary Razorpay product and integration choice

**Primary product:** Razorpay Payment Gateway, using Standard Checkout on the CRM public invoice page, server-created Razorpay Orders from the Hangers Node.js backend, trusted server-side verification/reconciliation, and the shared CRM ledger. This is the primary collection architecture. Razorpay Payments on WhatsApp is an additional, separately gated channel; it does not replace the Payment Gateway integration.

**Selection rationale:** Hangers has a stateful, website-backed CRM invoice workflow that must bind each attempt to the current invoice balance and update finance records automatically. Standard Checkout keeps payment entry/authentication within Razorpay Checkout while preserving server-side order creation and verification. Quick Integration is not selected because Razorpay documents its customization limitations; Custom Checkout/S2S is not selected unless a documented requirement cannot be met with Standard Checkout. Hangers must not collect or process raw card details itself.

**Documentation scope rule:** Review all Payment Gateway topics and relevant subtopics for this CRM web + Node.js server integration. Record why other families (separate customer app, ecommerce plugins, and unrelated Razorpay products) are excluded. A page is not considered reviewed merely because it appears in navigation; status must reflect content actually inspected and mapped to code/tests.

## Product and accounting rules

- Razorpay is the payment processor and source of provider-side payment/settlement facts. The CRM ledger is the source of truth for Hangers invoices, allocations, receipts, refunds, balances, and reports.
- A browser success callback is not proof of payment. A payment becomes collected in CRM only after trusted server-side verification confirms the provider payment is captured (or an authenticated, validated provider event is reconciled against Razorpay).
- `authorized` is not `captured`; do not post it as paid. Keep it pending until a captured/paid fact is verified.
- Each invoice checkout has a stable local identity and corresponding Razorpay Order. A retry for the same unchanged invoice balance reuses that same provider Order so Razorpay can group payment attempts and handle late authorisation; a changed amount/mode/currency must fail closed for finance reconciliation, not silently create a second payable Order while the first may still resolve. Record every retry and state transition in the audit trail.
- Every captured payment is applied through the canonical payment service in a database transaction. This must create the payment ledger entry, invoice allocation, receipt/receipt allocation, and update invoice/order balances and statuses atomically. The existing payment service remains the canonical path; no controller should hand-write payment/order status as a shortcut.
- Provider events are at-least-once and may arrive late or out of order. Deduplicate by Razorpay event ID and payment ID, and make every state transition safe to replay.
- A webhook must be durably accepted before returning success to Razorpay. Transient processing failures must remain retryable; permanent business mismatches must be retained as actionable exceptions, not silently discarded.
- Razorpay gross collection, refunds, fees/taxes, net settlement, settlement adjustments, and bank credit are separate financial facts. Never label a captured payment as a bank deposit.
- Bank reconciliation cannot be claimed as automatic until Hangers has an authenticated bank feed or imports a bank statement. Until then, show Razorpay settlement state separately and provide controlled statement import/matching with unmatched exceptions.
- WhatsApp is a notification side effect, not proof of payment. Queue it after the ledger transaction commits; record delivery outcome independently. Notification failure must not roll back a real payment.
- Razorpay Payments on WhatsApp is an optional one-time payment channel, not a replacement for Hangers' existing WhatsApp messaging provider, CRM invoice links, or payment ledger. It may only be enabled after Razorpay/Meta and the current WhatsApp provider confirm that Hangers' WABA ownership and API setup support the documented integration. It must settle into the same canonical CRM ledger and be reconciled from trusted payment facts.
- All payment operations must be safe for repeated requests and concurrent webhook/browser events. Never log API keys, webhook secrets, signatures, full card/bank data, OTPs, or unrestricted customer/payment payloads.
- **Test contact invariant:** Every Razorpay Test Mode checkout, regardless of hosting environment, must use exactly **+91 9930367267** and fail closed unless `RAZORPAY_TEST_CONTACT_NUMBER=9930367267` is configured. This is the sole permitted test number, including Razorpay's saved/pre-authenticated Checkout identity; do not use, fall back to, or retry with another number. Never alter an existing CRM customer's phone or link dummy invoices to their history just to satisfy this test. The override must never affect Live Mode, which always uses the invoice customer's contact.
- **Hard stop before OTP/payment:** Before every Test Mode attempt, personally inspect the actual Razorpay Checkout UI and verify its selected or pre-authenticated identity visibly shows exactly **+91 9930367267**; inspect again immediately before OTP entry/payment authorization. CRM data, environment configuration, a browser profile, cookies, or a prior checkout is not evidence of the current Checkout identity. If the number/account is missing, ambiguous, or anything else, stop immediately, close Checkout, and submit neither OTP nor payment. Correct the Test Mode identity/setup, open a fresh checkout, and verify again; never switch to or retry with an alternate identity. Automated tests must assert the configured contact; manual checkout acceptance requires both visual checks. This gate is test-only and must never change a real invoice customer's contact or affect Live Mode.
- **Active-goal acceptance gate:** The Razorpay implementation goal remains active until implementation, required no-skip test evidence, manual Test Mode checkout verification under the hard stop above, and all other acceptance criteria are complete. Do not report completion based only on code or local tests.
- **Per-attempt identity check:** Treat every checkout as a new verification boundary, including retries and saved/pre-authenticated sessions. Never infer the displayed Razorpay identity from CRM data, browser profile, cookies, environment configuration, or a previous checkout. Before each OTP/payment action, the visible Checkout identity must be **+91 9930367267**; otherwise stop with no provider action. Unit/integration tests must assert the sole configured Test Mode contact and must not trigger OTP/payment.
