## Purpose

Build a Hangers-branded, device-responsive checkout page that customers reach by selecting Pay on a public invoice. Payment options are displayed as a clear, one-option-per-row list. Razorpay processes payments and bank/app authentication through its documented integration. Hangers owns its payment form, script security, sensitive-data boundaries and applicable compliance obligations, as well as server-side order creation, signature verification, capture/settlement handling and webhook reconciliation. Using the SDK is not a blanket exemption from merchant compliance; Native OTP has separate PCI prerequisites.

This is an implementation specification and status record. Razorpay behavior and request formats below are sourced only from Razorpay's official documentation. Do not introduce payment-network logos, third-party checkout scripts, payment API behavior, or external design assets without explicit user approval. The Razorpay JavaScript SDK must load from Razorpay's documented CDN. The Hangers brand mark is the existing first-party asset.

### Zero-Guesswork Rule

- Do not hard-code enabled payment methods, providers, UPI apps, banks, wallets, EMI plans, network logos, or accepted network claims. Read options from the documented Razorpay SDK/API response and use its returned identifiers as submitted values.
- Do not invent, rename, or synthesize Razorpay error codes/reasons. Preserve fields returned by Razorpay (`code`, `description`, `source`, `step`, `reason`, and metadata); locally authored validation and connectivity messages must not be presented as Razorpay errors.
- If Razorpay does not return a method list, show no payment options and provide a non-payment retry action. Do not display guessed fallback methods.
- Razorpay's guide documents a minimal static fallback set when the `ready` network call times out. This implementation intentionally does not use that fallback: during the outage, enabled account methods cannot be verified, and the user explicitly prohibited guessed fallbacks. The trade-off is temporary checkout unavailability instead of presenting a method that may not be enabled.
- Do not infer card-network identity or acceptance from partial BIN-prefix tables. The documented methods response only establishes account-level method availability; Razorpay validates the card/network during payment.

## Required Customer Flow

1. Customer opens a valid public invoice or customer outstanding-balance link.
2. The invoice displays the amount due and a Pay action. That action navigates to `/invoice/{slug}/checkout`; it does not create an order or open an embedded payment dialog.
3. The dedicated checkout page shows Hangers branding, invoice/order references, amount due, a responsive progress breadcrumb, and payment methods as separate full-width rows.
4. Recover the scoped persisted attempt/status before offering another payment. Load Razorpay's `razorpay.js` SDK from its official CDN, instantiate with the server-returned Key ID, wait for `ready`, and display the verified eligible methods. Previously paid/pending/review states take precedence over a fresh payment form.
5. After the customer selects a method, prepare or recover the order through the existing idempotent server endpoint before enabling final Pay. Bind the complete amount/currency/allocation version and any verified method-specific fee/eligibility inputs. Preparation may create a provider order, but never submits a payment. Rapid method changes/refresh cannot create unrelated orders; stale totals return to review rather than silently changing the payable amount.
6. Customer enters genuine required data, reviews the total and explicitly presses Pay. Call `createPayment` synchronously from this action with the prepared order; do not await a new order request and then hope the browser permits a popup. If a verified flow needs asynchronous validation after the click, use Razorpay's documented `paused: true` and `payment.resume`/`payment.cancel` lifecycle with an already bound order, without inventing a way to replace its ID. [Async Payments](https://razorpay.com/docs/payments/payment-gateway/web-integration/custom/features/async-payments).
7. Razorpay handles authentication, UPI app handoff/QR redirect, bank redirects and provider-side payment processing. Hangers preserves the same invoice recovery destination; it does not promise to eliminate bank/provider authentication windows merely because checkout has its own page.
8. On `payment.success`, send order ID, payment ID and signature to the existing server verification endpoint. The server resolves its own persisted order, verifies signature and independently checks payment binding/capture before settling. The callback URL and webhooks cover lost browser responses.
9. Captured status and webhooks remain authoritative for settlement/fulfilment. Unknown, attempted, authorized or pending attempts retain reconciliation. A created, never-attempted bound order can resume only under the verified policy. A failed snapshot alone does not prove money can never arrive later; replacement attempts require the recorded retry/late-success policy, not a timer or a generic terminal-failure label.
10. Enabled bank transfer is asynchronous: retrieve the bound virtual-account instructions and await authoritative credit reconciliation; instruction retrieval is not `payment.success` or proof of payment.

#### Page Ownership and Redirect Sequence

1. Hangers owns the invoice, amount/allocation summary, method selection, method fields, and waiting/recovery UI.
2. Razorpay SDK starts the payment on the customer's explicit Pay action. Card challenge/3-D Secure or OTP is displayed by Razorpay-controlled flow or issuer bank ACS as the provider determines. 3. Netbanking bank/provider owns credentials and authentication. Card EMI follows issuer/card authentication. Wallet/pay-later provider owns any sign-in/OTP surface. Exact screens are provider-dependent; do not promise a particular Hangers-versus-bank page where docs do not guarantee it.
4. UPI Intent switches to the selected supported PSP app; the customer authorizes with UPI PIN there and returns to browser/SDK. Start only from explicit action, wait for `payment.success`/`payment.error`, and do not treat app-switch/focus as a result. Razorpay documents `payment.cancel` handling.
5. Redirect UPI QR sends the customer to Razorpay's payment page, where Razorpay displays the QR. The separate beta non-redirect QR keeps the customer on Hangers and requires returned `qr_url`, `payment.upi.qr` created/expired lifecycle and account approval. Do not conflate these flows.
6. Use a callback POST only for a method/Custom Checkout configuration where the current Razorpay Custom Web contract documents `redirect: true` and `callback_url`; the UPI Intent child page explicitly documents POST success/failure delivery in that mode. Otherwise use the Custom SDK's documented event/handler contract. Confirm callback support and failure semantics for each enabled method before claiming universal redirect behavior. In either mode, browser data is untrusted: verify against server-bound order, fetch/reconcile provider status and settle only on authoritative captured status. Return to the same invoice/confirmation route with references; unknown remains under review and blocks blind duplicate payment.
7. Hangers customer-login OTP is a separate CRM identity flow, not a payment-authentication step.

## Errors, Retries, and Security

- While the SDK waits for a bank/app result, Check payment status exits the waiting form and invokes existing server status/reconciliation. Captured payments show the paid result; unresolved payments retain the status action and block another submission. Window-focus capture recovery also clears the payment form.
- Preserve Razorpay error fields `code`, `description`, `source`, `step`, `reason`, and available `metadata.order_id` / `metadata.payment_id` for CRM diagnostics. Show a useful customer message without claiming failure when outcome is unknown.
- A replacement attempt requires verified retry-policy applicability and retained late-success handling, not a failed snapshot alone. A created order with no attempts may resume its bound order under the verified policy. Any uncertain or processing result must block blind replacement and expose available Razorpay references and a status-check action.
- Never trust a browser-supplied order ID as the verification source. Resolve the expected Razorpay order ID from the persisted CRM attempt and use timing-safe signature verification.
- Do not log card number, CVV, expiry, or raw sensitive form data. Do not place such values in telemetry, browser storage, CRM requests, or tests other than mocked browser-to-SDK fixtures.
- Use the existing idempotent invoice checkout order creation, payment verification, reconciliation, webhook, and capture infrastructure. Do not create a parallel payment ledger.
- Custom checkout remains explicitly local Test Mode only until local acceptance and a separate deployment/readiness decision. Never submit a Live payment as part of local development or QA.
